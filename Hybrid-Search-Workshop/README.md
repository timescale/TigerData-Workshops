# Hybrid Search Workshop — BM25 + pgvector on Tiger Cloud

## Overview

This workshop builds a search engine over ~685 EV charging-station maintenance reports and compares three approaches, all in PostgreSQL:

1. **BM25 keyword search** — exact-term relevance ranking with `pg_textsearch`.
2. **Vector semantic search** — meaning-based similarity with `pgvector`'s HNSW index.
3. **Hybrid search** — **Reciprocal Rank Fusion (RRF)** of the two, combining keyword precision with semantic recall.

Keyword and vector search each have a blind spot. A search for *"animals chewing wires"* ranks a report about a raccoon-damaged **camera** at the top on word overlap, yet never finds *"Repaired damaged wiring caused by rodents"* — which shares no query words but is exactly what you want. Vector search finds that report instantly but can under-rank an obvious exact-keyword hit. **Hybrid search gets both.**

Embeddings are generated by a **small local model** (`fastembed`, `BAAI/bge-small-en-v1.5`, 384-dim). There is **no API key and no per-call cost** — everything runs against your Tiger Cloud service and your machine.

## Contents

- `hybrid-search.sql` — the workshop: extensions, schema, indexes, and the keyword / vector / hybrid queries (with expected results).
- `hybrid_search.py` — helper to load data, build embeddings, and run `search --mode keyword|vector|hybrid`.
- `ev_maintenance_reports.csv` — 685 maintenance reports (the searchable corpus).
- `requirements.txt` — Python dependencies.

## Prerequisites

- A Tiger Cloud service with these extensions available: `vector`, `pg_textsearch`.
- Python 3.9+.
- The repo-root `.env` with `TIMESCALE_SERVICE_URL` set.

## Getting Started

```bash
cd Hybrid-Search-Workshop
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 1. Create the table + BM25 index and load the 685 reports
python hybrid_search.py load-data

# 2. Embed every report locally and build the HNSW vector index
python hybrid_search.py build-embeddings
```

`build-embeddings` downloads the ~130 MB model once, then embeds all reports in a few seconds. It is incremental — re-running only embeds new rows.

## Try it

Search the same query three ways and watch the ranking change:

```bash
python hybrid_search.py search "animals chewing wires" --mode keyword
python hybrid_search.py search "animals chewing wires" --mode vector
python hybrid_search.py search "animals chewing wires" --mode hybrid
```

What to expect:

- **keyword** — top hits share the literal words *animal / chewing / wiring* (raccoon, mice, rat reports); a raccoon-**camera** report ranks #1 on word overlap, and paraphrases are missed.
- **vector** — surfaces *"Repaired damaged wiring caused by rodents"* as the top result **despite sharing no words** with the query.
- **hybrid** — RRF promotes the semantic winner to #1, lifts the reports both methods agree on, and drops the keyword-only false positive out of the top results.

The keyword query and "more like this" variants of the vector and hybrid queries also run as **plain SQL** — see `hybrid-search.sql`. Run its **query** sections after `build-embeddings`. Note the file's setup section begins with `DROP TABLE ... maintenance_reports`, so run that part **before** `load-data` — executing the whole file after loading would drop the loaded rows and embeddings.

## How hybrid search works (RRF)

Reciprocal Rank Fusion combines ranked lists without having to reconcile their different score scales (BM25 scores vs cosine distances). Each document's fused score is:

```
rrf_score = Σ  1 / (k + rank_in_list)      (k = 60 by default)
```

summed over the lists it appears in. A document ranked highly by **either** method scores well; a document ranked highly by **both** scores best. The fusion is a small SQL query (a CTE per method + a join) — no extra infrastructure.

## Notes

- **Local, private, free**: embeddings never leave your machine; no LLM/API key required.
- **Swappable model**: change `EMBED_MODEL`/`EMBED_DIMENSIONS` in `hybrid_search.py` (and the `vector(N)` column) to use a different fastembed model.
- **BM25 scores are negative** in `pg_textsearch` (`<@>` operator): more negative = better match; non-matching rows score 0.
